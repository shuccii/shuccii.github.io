# 余白の庭

Astroで作った個人サイトです。GitHub Pagesで公開しています。

## ローカル管理画面

```sh
npm ci
npm run admin
```

起動時に表示される `http://127.0.0.1:<port>/admin/` を開いてください。
管理用 `/admin/` は開発サーバーだけに存在します。公開サイトにも「✎ 編集」があり、PATで文章・ブログ・作品を編集できます。
サーバーはループバックに限定し、保存APIは同一Originと `.edit-secret` を検証します。
`.edit-secret` に長いランダムな編集パスワードを設定してください(Git管理対象外)。

ページ内テキストはローカルの `src/data/site.json` に保存します。
ブログ・写真・動画・作品の編集はGitHub Contents APIへ保存し、コミットと公開更新を行います。
公開する内容を確認してから保存してください。PATはブラウザのメモリだけで保持し、
タブを閉じると消えます。公開サイトの「✎ 編集」では同じPATを使います。

PATはfine-grainedで `shuccii/shuccii.github.io` だけを対象とし、
ContentsのRead and write権限と必要最小限の有効期限を指定してください。

管理画面から各ページへ移動して「✎ 編集」を押すと追加・変更できます。

- ブログ: タイトル、日付、説明、タグ、Markdown本文、画像・動画の添付
- 写真: jpg / jpeg / png / webp / gif
- 動画: mp4 / webm / mov

メディアは1ファイル50MBまでです。GitHubへの送信前にローカルサーバーで
位置情報を除去し、除去・確認に失敗したファイルは送信しません。

## 公開サイトのPAT編集

公開サイトの右下「✎ 編集」からPATを入力して編集できます。
PATはこのリポジトリだけのContents Read and write権限に限定してください。
ブラウザのメモリだけで保持し、localStorage/sessionStorageには保存しません。
保存先は固定GitHub APIです。紹介文・ブログ・作品の追加/編集/削除は従来どおりです。

写真・動画の追加もできます。公開サイトでは、選んだファイルをブラウザ内で処理して
位置情報を含むメタデータ（EXIF・XMP・IPTC、動画のメタデータ箱）を取り除いてから送信します。
元のファイルはGitHubへ送信しません。画素・映像・音声は再圧縮せず、画像の向きと色プロファイルは残します。
位置情報を記録するトラックを持つ動画、WebM、構造を読めないファイルは送信せずに止めます。
その場合はローカル管理画面から追加してください（`src/lib/media-strip.js`、`tests/media-strip.test.mjs`）。

## 写真・動画の位置情報

```sh
npm run privacy:sanitize
npm run privacy:check
```

手動でファイルを追加した場合も、コミット前に実行してください。
撮影位置のメタデータを除去し、画像の向き・色プロファイルを保持します。
画像・音声・映像を再圧縮しません。ソースとビルド成果物を検査し、
位置情報が残った場合はビルドを止めます。場所が写っている画像自体や
本文・ファイル名の情報は人が確認する必要があります。

現在のファイルを置き換えても過去のGitコミットにある原本は残ります。
既に公開した位置情報の回収は保証できません。履歴削除には別の対応が必要です。

## 作ったもの(/works/)

出版物・発表、アプリ・ツール、Webサイトを `/works/` に載せられます。

ローカル管理画面の `/works/` で「✎ 編集」を押すと、ブラウザから追加・編集・削除できます。
入力するのは、種類(出版物 / アプリ / Webサイト)、タイトル、公開日、説明、掲載先、
公開ページのURL、ソースコードのURL、使った技術、タグ、本文です。

本文を書くと詳細ページ(`/works/<ファイル名>/`)が作られ、一覧の見出しからそこへ進みます。
本文を空にすると詳細ページは作られず、一覧の見出しが公開ページのURLへ直接リンクします。

手で追加する場合は `src/content/works/` にMarkdownファイルを置きます。

```markdown
---
title: "論文・アプリ・サイトの名前"
type: "publication" # publication(出版物) / app(アプリ) / site(Webサイト)
date: 2026-09-18
description: "一覧に出る短い説明"
url: "https://doi.org/..." # 公開ページ・DOI。空でも可
repo: "https://github.com/..." # ソースコード。空でも可
venue: "雑誌名・学会名・ストア名など"
tech: ["Python", "scikit-learn"]
tags: ["研究", "機械学習"]
image: "" # src/assets/works/ に置いた画像のファイル名
---

本文(任意)。書くと詳細ページになります。
```

サムネイルを付けたいときは、画像を `src/assets/works/` へ手動で追加(コミット)し、
`image:` にファイル名を書きます。このフォルダの画像は写真ページには出ません。

## 背景画像・動画(手動管理)

サイト全体の背景スライドショーは `src/assets/backgrounds/` にあるファイルだけを使います。
写真・動画を投稿しても背景には自動で反映されません。背景に使いたいファイルは
`src/assets/backgrounds/` へ手動で追加(コミット)してください。

- 対応形式: jpg / jpeg / png / webp(画像)、mp4 / webm(動画)
- ファイルを削除すれば背景からも消えます

## コメント・いいね・非公開の意見ボックス

ブログ記事の末尾には、Supabaseを使ったコメント欄があります。
閲覧・投稿・返信・👍にログインは不要です。禁止語やスパムの検査を通過した
コメントは、送信後すぐに公開されます。

`/feedback/` は公開コメントとは別の非公開フォームです。アカウント登録なしで送信できますが、
内容はサイトに表示されず、管理者だけがSupabase Dashboardで確認できます。

初回設定:

1. Supabaseでプロジェクトを作成する
2. DashboardのSQL Editorで `supabase/write-limits.sql` → `supabase/comments.sql` → `supabase/private-feedback.sql` を順に実行する
3. `.env` に次を設定する

```env
PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

公開環境にも同じ2項目を設定してビルドしてください。`service_role` キーは
ブラウザやGitHubリポジトリへ絶対に置かないでください。

既に旧版の `comments.sql` を実行済みの場合は、
`supabase/enable-immediate-comments.sql` も一度だけ実行してください。

### 管理者によるコメント削除

削除操作はサイトの公開キーには許可していません。管理者はSupabase Dashboardで
`Table Editor` → `site_comments` を開き、対象行を選択して削除できます。
非表示だけにしたい場合は `status` を `rejected` に変更してください。

### 非公開の意見を確認する

Supabase DashboardのTable Editorで `site_feedback` を開きます。確認済みの意見は
`status` を `new` から `read` に変更できます。ブラウザ用の公開キーには
このテーブルの読み取り権限を付与していません。
送信はサイト全体で1分5件・24時間50件までです。ブラウザUUID単位の1時間5件制限は補助で、本人を識別する認証ではありません。識別子はハッシュ化して保存します。

## アクセスの記録を見る(自分だけ)

閲覧状況を Supabase に記録し、合言葉付きの `/visits/` で自分だけが見られるようにしています。
Cloudflare Web Analytics では分からない県・市、参照元、回線、再訪、滞在時間を見るための仕組みです。

- 記録する項目: ページのパス、粗い地域(国・都道府県・市区町村)、回線の提供元(例: 大学名・
  プロバイダ名と AS 番号)、参照元のドメイン名、端末の種類(スマートフォン/タブレット/パソコン)、
  ブラウザと OS の種類、言語、セッション最初のページか、再訪か、画面に表示されていた秒数
- 保存しない項目: IP アドレス、User-Agent の原文、参照元の URL 全体(パス・検索語)、個人を追跡する識別子
- 再訪の判定は、ブラウザ内に置いた「前回開いた時刻」だけで行い、その値はサーバに送りません。
  端末やブラウザを変えた場合、保存領域を消した場合は新規として数えます
- 地域と回線は閲覧者のブラウザから [ipwho.is](https://ipwho.is/)(応答がなければ
  [GeoJS](https://www.geojs.io/))に問い合わせて判定します
- ブラウザが Do Not Track / Global Privacy Control を出している場合は記録しません
- 同じセッション中の同じページは1回だけ数えます。記録は2年で消えます
- `localhost` では記録しません(開発中の閲覧は混ざりません)

初回設定:

1. Supabase の SQL Editor で `supabase/visits.sql` を実行する(項目を追加したときも、
   これをもう一度実行すれば既存の記録を残したまま列と関数が更新されます)
2. 同じ SQL Editor で、管理ページの合言葉を登録する(長い文字列にしてください)

```sql
insert into public.site_admin_keys (name, key_hash)
values ('visits', encode(extensions.digest('ここに長い合言葉', 'sha256'), 'hex'))
on conflict (name) do update set key_hash = excluded.key_hash;
```

確認方法: `/visits/` を開き、合言葉と期間を入れて「表示」を押します。
概要(訪問数・新規/再訪・平均滞在時間)、参照元、端末、ブラウザ・OS、回線の提供元、言語、
国別・都道府県別・市区町村別・ページ別・直近の閲覧が表示されます。
都道府県は日本語(例: 奈良県)で、市区町村は判定元の表記(例: Ikoma)で出ます。

このページはナビゲーションには載せておらず、`noindex` と `robots.txt` で検索避けしています。
合言葉を知らないと中身は取得できません(ブラウザ用の公開キーでは表のデータを直接読めません)。

地域は IP アドレスからの推定なので、携帯回線や職場のネットワーク経由では実際の場所と
離れた県・市が出ることがあります。

## 匿名RPCの書き込み制限（2026-10-07）

`write-limits.sql` の内部関数が、送信者のUUID・ページ・ロールによらない共通予算を検査します。
公開RPCの直接呼び出しにも同じ制限を適用し、内部関数と履歴には匿名・認証済みロールの権限を付与しません。

| 操作 | サイト全体の1分上限 | 過去24時間上限 | 保存件数上限 |
| --- | ---: | ---: | ---: |
| コメント | 10 | 100 | 全体20,000・記事ごと500 |
| GOOD（解除を含む） | 60 | 1,000 | 100,000 |
| 非公開意見 | 5 | 50 | 10,000 |
| 訪問記録 | 120 | 5,000 | 250,000 |

上限や同時書き込みに達すると、投稿・GOOD・意見は再試行を促すエラー、訪問記録は保存せず終了します。
既存データを削除せず、上限以上の場合も新規追加を拒否します。GOODの解除は保存件数上限でも可能です。
コメント取得は最大500件（古い順）です。500件を超える既存記事は最初の500件を表示し、新規コメントを受け付けません。

これは保存量・書き込み頻度を制限する仕組みです。同一人物の識別、1人1票、スパムの完全排除は保証しません。
攻撃者が共通予算を使い切ると正常な利用者も一時的に送信できません。公開API自体のリクエスト負荷には前段の制限が別途必要です。

既存プロジェクトの更新は、管理者のSQL Editorで `supabase/security-upgrade.sql` を全文実行してください。
共通制御と全RPCを1トランザクションで更新します。既存コメントを公開へ変更する旧移行は含めません。
同じ管理者ロールで関数を作成してください。新規設定時もこのSQLだけで全テーブル・関数を作成できます。
`enable-immediate-comments.sql` を後から再実行してもコメントの共通制限は残ります。
訪問レポートの不正な合言葉は直ちにエラーを返し、DB内の待機処理は行いません。長いランダムな管理用合言葉を使ってください。

検証: `npm run test:security` はPGliteの隔離PostgreSQL/pgcryptoで実際のSQLを実行します。
匿名権限、UUID・ページ・ロール変更、分/日上限、保存件数上限、通常投稿・返信・GOOD解除、旧移行と認証失敗を確認します。
単一接続のPGliteでは複数DB接続間のロック競合・稼働Supabase設定は検証できません。

### 本番への適用確認

GitHubへのpushはSupabaseのSQLを更新しません。管理者が
`supabase/security-upgrade.sql` を適用した後、`supabase/verify-production.sql`
の読み取り検証で全項目がtrueになることを確認してください。
コード上の制限と本番の適用状態を別々に扱います。
